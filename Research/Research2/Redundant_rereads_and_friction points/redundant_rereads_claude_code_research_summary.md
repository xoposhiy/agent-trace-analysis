# Redundant File Re-Reads in Claude Code: Token Waste, Causes, and the Root-Cause Research Gap

*A research summary establishing, in logical order: (1) how much of an agent's token budget is consumed by reading/context; (2) how much of that reading is repeated re-access of the same files; (3) how much of that repetition is strictly redundant and recoverable; (4) the methods (context pruning / trajectory reduction) that show this waste can be eliminated; and (5) whether any prior work uses an LLM-as-a-judge to root-cause repetitive re-reads from traces. All quantitative claims are sourced with clickable links after each paragraph.*

---

## Part 1 — How much of the token budget goes to reading / context

Reading files, not editing or executing, is where the token budget is spent. On SWE-bench Verified with the Mini-SWE-Agent framework and Claude Sonnet 4.5, read-type operations (file/directory inspections such as `cat`, `grep`, `head`) consumed an overwhelming **76.1% of total tokens (~4.38 million)**, far exceeding execute (12.1%) and edit (11.8%) combined. Reads dominate because of two compounding effects: coarse-grained file streaming (the agent dumps entire files or thousand-line blocks into context to understand an unfamiliar codebase) and an accumulation effect (the full conversation history is carried into every subsequent round, so earlier reads persist and snowball). Edits and executions, by contrast, produce targeted outputs that do not dump raw source into the history. *Source: [SWE-Pruner, arXiv:2601.16746](https://arxiv.org/abs/2601.16746).*

This pattern is corroborated by independent trace tooling: the `claude-trace` corpus attributes roughly **56% of the token budget to the Read tool**. Reads are therefore the single largest lever on token cost, which is why redundant re-reading specifically matters. *Source: [claude-trace (vexorkai)](https://github.com/vexorkai/claude-trace).*

## Part 2 — How much of that reading is repeated re-access of the same files

A large share of file actions are repeats of files the agent has already accessed. Analyzing OpenHands trajectories on SWE-bench Verified, higher-cost models — including **Claude Sonnet 4**, Qwen3-Coder-480B, and Kimi-K2 — perform more file actions, and **around 50% of those actions are repeated actions on the same file**, reflecting exploratory and redundant back-and-forth access rather than steady progress. For Claude Sonnet 4 specifically, an average of **14.20 file-view actions per task** were recorded, of which **7.17 (~50%) were repeated views** of files already seen; a similarly high share of its file modifications were also repeats. Token-efficient models (GPT-5, GPT-5.2) perform far fewer file actions and far fewer repeats, indicating efficiency depends not just on the number of actions but on how non-redundantly they are executed. *Source: [Bai et al., "How Do AI Agents Spend Your Money?", arXiv:2604.22750](https://arxiv.org/abs/2604.22750).*

The behavior is sensitive to codebase quality, which both quantifies the phenomenon and points to a remedy: **when the codebase is clean, re-reading drops sharply.** In a controlled minimal-pair study, agents working on cleaner code returned to already-edited files **34% less often (−34% file revisitation)** and used **7.1% fewer input tokens and 8.5% fewer output tokens**. The authors interpret revisitation as the agent acting on "uncertainty about a previous edit" rather than legitimate exploration — when the code was cleaner, the agent could commit to an edit and move on instead of looping back to double-check. *Source: [Code-Cleanliness minimal-pair study, arXiv:2605.20049](https://arxiv.org/abs/2605.20049).*

The study does not advance a strict formal definition of "clean code," instead using the term for a family of characteristics traditionally associated with maintainable software: small, single-purpose functions with descriptive naming; easy-to-follow control flow; and minimal dead code, duplicated logic, or accidental coupling between unrelated parts of the system. To quantify these traits in the minimal-pair test, the researchers relied on the static analyzer **SonarQube**, operationally defining code as "cleaner" when it has **fewer static-analysis rule violations (issues) and lower cognitive complexity**. The minimal pairs were cleaner and messier versions of repositories perfectly matched in architecture, dependencies, tests, and external behavior; the cleaner variants achieved their status by actively resolving flagged issues — deduplicating string literals, removing commented-out code and dead branches, replacing legacy idioms, and refactoring massive "god structures" (such as 200-line dispatch switches) into smaller, named helper functions. The practical implication for re-read reduction: a user who keeps the codebase clean (by these measures) sees materially less agent revisitation and lower token use, with no loss of solve rate. *Source: [Code-Cleanliness minimal-pair study, arXiv:2605.20049](https://arxiv.org/abs/2605.20049).*

Re-editing (edit-thrashing) is a real but smaller, more failure-correlated mode than re-reading. IDE-Bench operationally defines **thrashing/backtracking as more than 4 edits to the same file** and **context loss as more than 5 reads of the same file**, finding thrashing in **28.2%** and context loss in **27.6%** of failed runs, with the two co-occurring in nearly 19% of failed runs — a characteristic "lose track of requirements, then ping-pong on edits" failure trajectory. Notably, **Claude Sonnet exhibited context loss in 74.6% of its failed runs**: unlike weaker models that fail by editing blindly before exploring, frontier Claude generally explores adequately but fails by non-convergence — losing the plot as the context grows and getting stuck in an unstable read/edit loop instead of finalizing. *Source: [IDE-Bench, arXiv:2601.20886](https://arxiv.org/abs/2601.20886).*

## Part 3 — How much of that repetition is actually, strictly redundant (recoverable waste)

The raw ~50% repeat rate is **not** the waste rate — much repetition is forced (post-compaction recovery, file changed on disk) or legitimate (verify-after-edit, a different line range). The strictly redundant, recoverable subset is much smaller. The single hard, retroactive measurement on **107 real Claude Code sessions** found **1,225 redundant reads totaling 1.9M of 23.5M tokens — exactly 8.0% of all tokens** — when counting only same-file, same-range, unchanged, still-in-context re-reads (explicitly excluding compaction-evicted, post-edit, and different-range reads). *Source: [egorfedorov, "Read Cache" 107-session analysis (DEV Community)](https://dev.to/egorfedorov/update-my-claude-code-token-optimizer-now-blocks-redundant-reads-heres-the-data-from-107-27lj).*

A broader category — "recoverable context waste" (redundant + useless + expired content, not only strict re-reads) — is estimated at **~30–60% of read/context tokens**, i.e., roughly 30–60% of read tokens could be removed and the agent would still finish the job. This figure is medium-confidence: it is directionally consistent across sources but each defines the category slightly differently and several are self-reported. The takeaway is a nested picture — the ~50% repeat rate overstates recoverable waste by roughly 2–5×; strictly-redundant re-reads are ~8% of *total* tokens; and the wider recoverable-context bucket is ~30–60% of *read* tokens. *Sources: [AgentDiet, arXiv:2509.23586](https://arxiv.org/abs/2509.23586); [SWE-Pruner, arXiv:2601.16746](https://arxiv.org/abs/2601.16746); [egorfedorov "Read Cache" (DEV Community)](https://dev.to/egorfedorov/update-my-claude-code-token-optimizer-now-blocks-redundant-reads-heres-the-data-from-107-27lj).*

## Part 4 — Evidence that this waste can be eliminated (the three reduction papers)

Three reduction systems demonstrate that the redundant read/context volume is removable without hurting task success — the key proof that the waste is genuinely recoverable rather than necessary work.

**AgentDiet** uses an inference-time reflection module to remove **useless, redundant, and expired** trajectory content, reducing **input tokens by 39.9%–59.7%** and total computational cost by 21.1%–35.9% while maintaining the same agent performance, evaluated on coding-agent trajectories. It also reports a directly causal observation from its traces: on long contexts, models can degrade into "repeating the same tool call until the step limit is reached." *Source: [AgentDiet, arXiv:2509.23586](https://arxiv.org/abs/2509.23586).*

**SWE-Pruner** prunes file-read context with a small trained skimmer and reports **23–54% token reductions** across benchmarks (for Claude Sonnet 4.5, total tokens dropped ~23% with stable success), targeting exactly the read-dominated, snowballing context that drives the 76.1% read-token share. *Source: [SWE-Pruner, arXiv:2601.16746](https://arxiv.org/abs/2601.16746).*

**FastContext** offloads repository exploration to a dedicated subagent so exploratory reads never enter the main solver's history, reducing main-agent token consumption **up to 60%** while maintaining or improving resolution rates. *Source: [FastContext, arXiv:2606.14066](https://arxiv.org/abs/2606.14066).*

**Important scope note:** these three are research systems that operate *inside the agent loop* — they are not features a Claude Code end user can toggle. Their headline percentages (≈40% / ≈40–60% / ≈60%) describe what is achievable with harness engineering, not what a Claude Code user gets out of the box. *Sources: [AgentDiet, arXiv:2509.23586](https://arxiv.org/abs/2509.23586); [SWE-Pruner, arXiv:2601.16746](https://arxiv.org/abs/2601.16746); [FastContext, arXiv:2606.14066](https://arxiv.org/abs/2606.14066).*

## Part 5 — What a Claude Code user can actually do (suggestions mapped to root-cause buckets)

Root-cause buckets for redundant re-reads: **(A) post-compaction eviction**, **(B) context bloat**, **(C) exploration thrash**, **(D) genuine in-context redundancy**.

The highest-leverage user remedies are native and zero-setup. Proactive `/compact` locks in a clean summary before quality degrades (addresses A, B); `/clear` at task boundaries prevents stale context being re-billed every message (B); plan mode forces a plan before file operations, reducing the read-then-thrash-then-re-read pattern (C); subagent delegation gives exploration its own fresh context window so only a compact summary returns to the main thread (C, D); trimming `CLAUDE.md` to under 200 lines and moving specialized instructions to on-demand Skills reduces fixed context (B); disabling unused MCP servers via `/mcp` and inspecting with `/context` reclaims window space (B); and targeted `offset/limit` reads plus a one-file codebase map let the agent read one file instead of twenty (C, D). *Sources: [Claude Code "Manage costs" docs](https://code.claude.com/docs/en/costs); [Claude Code MCP docs](https://code.claude.com/docs/en/mcp); [Anthropic "Effective context engineering"](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents); [FastContext, arXiv:2606.14066](https://arxiv.org/abs/2606.14066).*

One one-time install directly blocks the strictly-redundant bucket: a **`PreToolUse` read-cache hook** (read-once / "Read Cache") records each read (path + mtime + range), then blocks a re-read of an unchanged file whose range is already loaded, while invalidating on Edit/Write (content changed), on compaction (context genuinely lost → re-reads allowed), and on a configurable TTL. It targets (D) directly and respects (A) by design, installs to `~/.claude/`, and needs only `jq`/`bash` or Node. *Sources: [read-once hook (DEV Community)](https://dev.to/boucle2026/read-once-a-claude-code-hook-that-stops-redundant-file-reads-4bjk); [egorfedorov "Read Cache" (DEV Community)](https://dev.to/egorfedorov/update-my-claude-code-token-optimizer-now-blocks-redundant-reads-heres-the-data-from-107-27lj).*

At the API level, Anthropic also offers tool-result clearing (`clear_tool_uses_20250919`) and server-side compaction (`compact_20260112`, available for Claude Opus 4.6 and Sonnet 4.6) as the recommended automatic strategies (A, B). *Source: [Anthropic "Effective context engineering"](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents).*

## Part 6 — Can an LLM-as-a-judge root-cause repetitive re-reads from traces? (the search result)

A targeted literature search was conducted for prior work that root-causes repetitive/redundant file re-reads from agent traces — ideally Claude Code traces, and ideally using an LLM-as-a-judge. The conclusion: **no published paper performs this exact study.** Root-causing repetitive file re-reads in Claude Code (or general coding-agent) traces — and doing so with an LLM-as-a-judge specifically — is a genuine, unfilled research gap as of mid-2026.

The single closest paper is **"Process-Centric Analysis of Agentic Software Systems"** (arXiv:2512.02393; preprint Dec 2, 2025; published PACMPL/OOPSLA1 2026, DOI 10.1145/3798271; Liu, Chen, Krishna, Sinha, Ganhotra & Jabbarvand, UIUC + IBM Research). It analyzes **4,000 trajectories ("Graphectory")** from SWE-agent and OpenHands across four models (DeepSeek-V3, DeepSeek-R1, Devstral-small-2505, and **Claude Sonnet 4**) on SWE-bench Verified (12 repositories). It defines a **"RepeatedView" anti-pattern**, described verbatim as: *"RepeatedView occurs when the agent revisits the same structural region, e.g., a file, multiple times during navigation, reflecting redundant inspections of identical code, often after unsuccessful edits or incomplete localization."* Crucially, the attributed CAUSE is explicitly **edit-failure / incomplete-localization dynamics** — for example, "after two failed edit attempts (step 9), the agent reopens client.py … for better localization" — and the paper does **NOT** attribute re-reads to context loss, compaction, or memory failure; its framing is strategic/behavioral inefficiency. Its full anti-pattern taxonomy spans a localization phase (RepeatedView, ZoomOut, Scroll, OverlyDeepZoom) and a patching phase (UnresolvedRetry, EditReversion, StrNotFound, NoEffectEdit, AmbiguousTarget), and it observes that unresolved trajectories "have more back edges, demonstrating more repetitions." This is the best existing prior art for root-causing re-reads from traces — but it does so via localization dynamics, treats re-reads as one anti-pattern among nine, and uses deterministic process-mining rather than an LLM-as-a-judge. *Source: [Process-Centric Analysis of Agentic Software Systems, arXiv:2512.02393](https://arxiv.org/abs/2512.02393).*

(The exact prevalence percentage for RepeatedView in the paper's Table 3 could not be extracted verbatim; what is confirmed is that all reported anti-patterns clear a ≥10%-prevalence / 95%-CI threshold across the 4,000 trajectories, sampled via 600 instances.) *Source: [Process-Centric Analysis of Agentic Software Systems, arXiv:2512.02393](https://arxiv.org/abs/2512.02393).*

**Feasibility verdict.** The approach is feasible in principle — the building blocks exist in adjacent work (LLM judges can already compute a redundancy fraction over tool calls, LLM reflection modules can already label redundant content in coding trajectories) — but its *reliability* on re-reads specifically is unestablished, and the one paper that does root-cause re-reads from traces (RepeatedView) does so deterministically and attributes them to localization dynamics rather than context loss. The defensible design for any future attempt is therefore a hybrid: **deterministic trace tooling first** (path-level grouping, compaction-boundary and edit-adjacency checks, range-overlap), with an **LLM-as-a-judge applied last**, only on the ambiguous residual, with confidence scores and human spot-checks. *Source: [Process-Centric Analysis of Agentic Software Systems, arXiv:2512.02393](https://arxiv.org/abs/2512.02393).*

## Caveats

- **The ~50% repeat rate is a raw count, not a waste rate;** it overstates strictly-recoverable waste by roughly 2–5×. The strictly-redundant figure is ~8% of total tokens; the broader recoverable-context figure is ~30–60% of read tokens.
- **Source tiers differ.** Peer-reviewed/arXiv: SWE-Pruner, Bai et al., Code-Cleanliness, IDE-Bench, AgentDiet, FastContext, and Process-Centric Analysis (OOPSLA1 2026). Vendor/blog (directional, often single-user, self-reported): the 8.0% 107-session figure, the read-cache hook savings, the claude-trace 56% corpus figure, and the ~30–60% upper-range claims.
- **Definitions vary across papers** (read-token share vs. repeated-action count vs. redundant/useless/expired content vs. strict same-range re-read), so figures corroborate direction and magnitude but are not directly interchangeable.
- **Model-version coverage is uneven:** strongest data is on Sonnet 4 / 4.5; Sonnet 4.6 appears mainly in the Code-Cleanliness revisitation delta, and no trace-level strictly-redundant figure exists yet for Opus 4.6.
- **No published work root-causes repetitive file re-reads from Claude Code traces, and none uses an LLM-as-a-judge for this specific task** — this is the identified research gap. Feasibility is supported by adjacent building blocks; reliability on re-reads is unestablished, and step-level attribution accuracy in the literature is low (≈14–46%).
